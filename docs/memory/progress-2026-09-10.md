## 2. 决策演进（本期最重要）

### 2.1 事件总线：五步收敛

```
暂缓（等 R3）→ v0.4「最小版」自研类型化总线 → v0.5「双实现」（自研 + R3 封装）
  → v0.6 命名统一（IZEventBus / ZEventBus / ZR3EventBus）
  → v0.7（使用者修订）收敛为「单实现 + R3 桥」：IZEventBus + ZEventBus（Core 唯一实现）
       + R3 桥（AsObservable 扩展，依赖 R3 的程序集，不进 Core）
```

**收敛依据（v0.7，写在 core-design §4.3）**：R3 没有按类型路由的全局注册表（`Subject<T>` 是命名实例，仍要人工传递）；Rx `OnError` 会终止整条流，与总线"单订阅者抛异常 → 继续通知其余"冲突，故 R3 版总线必然复制一份自研内核；桥比第二实现更小更强且可事后补；R3 版放 Core 破地基分层、放 UI 层则依赖方向倒挂。

**最终纪律**：总线只做**路由**、R3 只做**加工**；同一件事只发布一次，需要节流/合并的一方在**订阅侧**（R3 桥）加工；UI 通知也走总线（不再分两条）。

**已知代价（写进文档）**：桥之后的 Observable 链上抛异常属 Rx 语义（使用方自理），总线侧仍以为订阅存在——实现 UI 时建议链尾统一兜底。

### 5.3 待裁决：core-design §4.3 的一条决策依据需修正（事实性问题）

- 文档现状（v0.7）依据第 2 条写："Rx 语义中 `OnError` **终止整条流**，与总线异常隔离要求冲突，故 R3 版总线必然复制自研内核"。
- **事实**（R3 1.3.1 官方 README）：「in normal Rx, when an exception occurs ... it flows to `OnError` and the subscription is unsubscribed, but **in R3, it flows to `OnErrorResume` and the subscription is not unsubscribed**」——R3 刻意改掉了自动退订；并提供 `OnErrorResumeAsFailure()` 恢复旧语义、`IgnoreOnErrorResume()` 忽略异常、`RegisterUnhandledExceptionHandler` 兜底。
- **影响**：该论据对 R3 不成立；但 v0.7 的**结论（单实现 + R3 桥）不受影响**——其余四条依据（R3 无按类型路由的全局注册表、成本在纪律、桥更小更强、地基分层不破）依然成立。
- **处理**：等使用者决定是否修订该条措辞（AI 不擅自改使用者的决策记录）。
