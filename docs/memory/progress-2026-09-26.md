## 2. 本期定案（音频模块）

| 事项 | 结论 |
|---|---|
| **D2 tick 驱动** | **`ITickable`**（方案 A）。`ITickable` 放在**实现类**上，**不放接口**（否则 VContainer 类型污染对外契约、测试替身被迫实现 `Tick()`）；注册 `Register<IZAudioManager, ZAudioManager>(Lifetime.Singleton).As<ITickable>()` |
| **D3 fade 推进** | **各自 UniTask 循环**（壳内 per-instance `CancellationTokenSource`）；tick **只**做"播完检测 + 归还"，不推 fade |
| **D4 池满** | 丢弃。池自身已记 **Error**（`已达到最大容量`），音频侧只记 **Warning**（避免重复刷屏） |
| **C1 `ZAudioOptions`** | `Mixer` / `InitialPoolSize` / `MaxPoolSize` / `MixerAddress`（Addressables 地址，可为空）+ 五个参数名 + 五个组名映射（`GetParam` / `GetGroupName`，实现里都是 `const`） |
| **C2 `ZAudioPlayOptions`** | `Bus` / `Volume` / `Pitch` / `Loop` / `FadeInSeconds`(float) / `SpatialBlend`(float)；**类型 class**（`= default` 即 null = "没传"，配 `?? DefaultOptions`）；**`Volume01` 更名 `Volume`** |
| **C3 `OnApplicationPause`** | v1 **不自动暂停**；移动端的 `PlayerPrefs.Save()` 时机交由使用方 |
| **`PlaySfxAsync` 去掉 `in`** | `in`/`ref`/`out` 与 `async` 方法**不兼容（CS1988）**，而该实现必须 `await` 加载 → 改值传递（class 无拷贝开销）。`PlaySfx`（同步）保留 `in` |
| **初始化归属（B 方案）** | 建 root/原型/池、加载 Mixer 都归 **`ZAudioBootstrapper.InitializeAsync`**（Phase=Audio，在 Resources 之后 → Addressables 已就绪）；`ZAudioBootstrapper` 实现 `IDisposable`（**接口只有 `InitializeAsync`，但实现类自己实现 `IDisposable` 就能拿到释放通道** —— 与 `ZLoggerBootstrapper` 同形）；`IZAudioManager.InitializeAsync` 因此**删除** |
| **销毁顺序（强制）** | `_audioManager.Dispose()`（停 BGM → 归还全部在播 → 释放 clip）→ `DestroyPool<PooledAudioSource>()` → `_mixerHandle.Release()` → 销毁原型 → 销毁 root |
| **BGM 句柄的池外语义** | `PlayBgmAsync` 返回的句柄以 `_item == null` 标识 BGM 模式，**不进播放表**（表只装池化音效），`Stop()` 走 `AudioBusChannel.Stop` 而非 `Return` |
| **音量双路职责** | **总线音量只走 Mixer**（`SetVolume` → `SetFloat(ToDb(v))`）；`AudioSource.volume` 只承载"单次 `Volume` + fade 插值"（曾出现双重衰减 = v² 的错误，已修正） |

- **已修的真实缺陷**（均为"只有跑起来才露头"）：
  1. 启动后**立刻**退出 → `MissingReferenceException: PooledAudioSource has been destroyed`（退出期 Unity 先行销毁池实例，而 `ClearItem`/归还路径仍访问它）
  2. 退出后 `资源 … Mixer … 未被释放, 持有者: ZAudioBootstrapper`（`_mixerHandle` 未 Release）
  3. BGM 快速切歌竞态：取消是异步的，旧循环的 `finally` 迟到 → 会停掉新请求刚起播的源（修法：`_crossPrev` + 取消时立即停 + `finally` 只在自然完成时清理）

## 4. 我（AI）犯过并已更正的错误（方法论留痕）

| 错误 | 更正 |
|---|---|
| 断言"`IZModuleBootstrap` 没有 Dispose 通道 → bootstrapper 无法释放资源" | **错**——接口确实没有，但**实现类自己实现 `IDisposable`** 就会被容器跟踪并调用（`ZLoggerBootstrapper` 即是先例）。**使用者当场指出**。教训：说"做不到"之前，先看有没有现成先例 |
| 断言"`ZObjectPool.cs:87` 的 `tItem.name` 对已销毁对象会抛 MissingReference" | **不准确**——`T : Component` 的 `==` 是 Unity 重载，已销毁对象在上一关 `if (tItem == null)` 就被判 null 了 → 实际后果是**记一条误导性的"类型不匹配"Error**，而非异常。教训：**接口类型与 Unity 类型的"判空语义不同"**（接口引用是 CLR 判空），定位前先把这条捋清 |
| 建议"`Dispose()` 里补一次 `PlayerPrefs.Save()`" | **次优**——[Unity 文档](https://docs.unity.cn/6000.4/Documentation/ScriptReference/PlayerPrefs.Save.html)：`Save()` 只负责落盘，而**Unity 在 `OnApplicationQuit()` 会自动保存**，且**官方明确不建议在游戏进行中调用**（写盘会造成卡顿）。真正有价值的时机只有移动端 `OnApplicationPause(true)`。使用者质疑后被纠正 |
| 一度以为"构造期能异步加载 Mixer"可行 | **不可行**，且**时机更早于 Addressables 初始化**：`ZBootstrapper`（`IAsyncStartable`）构造时经 `IEnumerable<IZModuleBootstrap>` 就创建了所有 bootstrapper → `ZAudioManager` 在**阶段执行之前**就被构造，此时 Resources 阶段尚未跑 |
| 未查证就断言"可以用 `FindObjectOfType` 找 Mixer" | **错**——[Unity 文档](https://docs.unity.cn/6000.4/Documentation/ScriptReference/Object.FindFirstObjectByType.html)：`FindFirstObjectByType` **doesn't return Assets**。`AudioMixer` 是资产 → 永远返回 null |

## 5. 本次查实的库/引擎事实（可复用）

| 事实 | 出处 |
|---|---|
| **VContainer 的 Dispose 是 LIFO** | `CompositeDisposable` 用 `Stack<IDisposable>` + `Pop`；实例在**首次创建时**入栈（`Container.cs:174-184`）→ 顺序 = **逆创建顺序**，不是注册顺序 |
| **`RegisterInstance` 传入的既有实例不被跟踪 Dispose** | `Container.cs:179`：`!(registration.Provider is ExistingInstanceProvider)` |
| **`ITickable` 的收集标准** | 按"注册的接口集合里显式含 `ITickable`"收集（`EntryPointDispatcher.cs:91` 解析 `ContainerLocal<IReadOnlyList<ITickable>>`）；`LifetimeScope` 自动注册 dispatcher（`LifetimeScope.cs:307`）→ 无需手动注册；tick 时机 = `PlayerLoopTiming.Update` |
| **`AudioSource.isPlaying` 在 `Pause()` 后返回 `false`** | [Unity 文档](https://docs.unity.cn/6000.4/Documentation/ScriptReference/AudioSource-isPlaying.html)原文注记 → **暂停中的音效会被"播完检测"误判为结束**，必须自己记 `_paused` 标志（已实现） |
| **`async` 方法不能有 `ref`/`in`/`out` 参数** | 编译器 **CS1988**（实测复现） |
| **编译错误会分层抑制** | `CS0246`（找不到类型）/`CS0535`（未实现接口成员）会让编译器**跳过方法体检查** → 修掉上层才会露出下层的 `CS0161` 等。排查时不要被"只剩 1 个错误"骗到 |
| **Unity Test Framework 不等待 `async Task` 测试方法** | UTF 的 runner 只认 `void` 与 `IEnumerator` → 写成 `public async Task Xxx()` 会被判失败。**识别特征：同一批里所有 async 测试全红、同步测试全绿**。修法：内部同步完成的场景改回同步 + `GetAwaiter().GetResult()`；真涉及异步（Addressables / 需要 PlayerLoop）则用 `[UnityTest] IEnumerator` |
| **接口实现方法的泛型约束必须与接口完全一致** | `IZObjectPoolManager` 的 `DestroyPool<T>()` / `ClearPool<T>()` **没有约束**（与 `CreatePool`/`Get`/`Return` 不同）→ 实现里多写 `where T : Component, IZObjectPoolItem` 会报 **CS0425**（这是个易踩的小不一致） |
| **`PlayerPrefs.Save()`** | 只在写盘；`OnApplicationQuit()` 自动保存；官方不建议游戏进行中调用 |
| **`FindFirstObjectByType` 不返回 Assets** | 只找已加载的**场景对象**（也排除 inactive 与 `HideFlags.DontSave`） |
