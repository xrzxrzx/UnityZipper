> 状态：**v0.6 草稿，待审阅**
> 定位：`docs/planning/technical-roadmap.md` §4.2 中 `Zipper.Core`（基础设施：日志、事件、扩展、公共工具）的展开设计稿。**只给设计思路与思路级伪代码，不含实现代码**。
> **实施归属**：AI 只负责架构设计与思路级伪代码（供设计参考）；**代码实现由使用者完成**。依据：`docs/standards/agent-role.md`。

## 1. Zipper.Core 的定位与边界

**是什么**：框架最底层程序集，提供所有上层模块（Pool / Resources / Audio / UI）都要用的基础设施。它**不认识任何业务概念**，也不认识其它 Zipper 模块。

**依赖原则（重要，与 roadmap §4.2 有一处刻意偏差）**：

| 依赖 | 是否允许 | 说明 |
|---|---|---|
| Unity 引擎 | ✅ 必须 | 日志走 Unity `Debug`、文件走 `Application.persistentDataPath` |
| UniTask | ⚠️ 可选 | v1 **不引**：日志设计为同步门面 + 自建后台泵，不必依赖 UniTask |
| VContainer / Addressables / DOTween / R3 | ❌ 禁止 | 保持零框架耦合，装配由上层 `Zipper.Runtime` 负责 |

> roadmap §4.2 写的是「所有 Zipper.* 运行时程序集需引用 UniTask / VContainer」——**Core 是例外**：它是最底层，引 DI 容器会反过来让所有模块被迫传递依赖，破坏"地基可独立裁剪"的目标。此处偏差建议记入 roadmap 修订项。

**管什么**：
1. **Logging**：分级日志、模块 tag、运行时开关、编译期剥离、Console + 文件双输出（本文重点，§3）
2. **Assert / Guard**：`ZAssert` 断言（编辑器中断 + Release 降级为 Error 日志）
3. **Extensions**：Unity 对象空判断、Transform/GameObject 便捷方法（**按需加，禁止一次性堆砌**）
4. **工具**：框架版本常量、时间/随机/路径小工具

**不管什么**：
- ❌ **不做 R3 的替代品**——事件总线只承担"跨模块低频通知"；UI 相关通知与响应式流交给 R3（§4.3），不用总线承载 UI 绑定
- ❌ 不做资源/池/UI 相关任何逻辑
- ❌ 不做下载进度、场景流程等业务编排

## 2. 模块总览

```
Zipper.Core
 ├─ Logging/
 │    ├─ ZLog（静态门面，可编译期剥离）
 │    ├─ IZLogger（模块化日志器，可注入、可测）
 │    ├─ IZLogSink → ConsoleSink / FileSink（可插拔输出）
 │    └─ 数据：日志级别 / 模块枚举 / 日志条目

 ├─ Assert/          ZAssert（编辑器断言 + Release 降级日志）
 ├─ Extensions/      UnityObjectExtensions 等（按需增补）
 └─ Utils/           框架版本常量、小工具（克制）
```

## 3. 日志系统设计（核心）

### 3.1 需求与约束

| 需求 | 决策 |
|---|---|
| 分级 | `Trace / Debug / Info / Warn / Error / Fatal` 六级 |
| 模块归属 | 每个日志带 tag（`Core`/`Pool`/`Resources`/`Audio`/`UI`/`Game`），Console 前缀如 `[Zipper.Resources]` |
| 输出目标 | **Console + 文件**双 Sink（文件落在 `persistentDataPath` 下） |
| Release 开销 | **Trace/Debug/Info 编译期剥离**；Warn/Error/Fatal 始终保留 |
| 运行时控制 | 全局 + 按模块动态改级别 |
| 线程安全 | 任意线程可调用；**Console 输出必须主线程**、文件写入可后台 |
| 性能 | 关闭级别时**零字符串分配**；文件 IO 不阻塞主线程 |
| 健壮性 | 日志系统自身异常不得影响游戏；退出时 flush 不丢尾日志 |

### 3.2 架构

```
   调用点                                  输出
┌──────────────────┐   ┌──────────────┐   ┌────────────────┐
│ ZLog.Info(...)   │   │              │   │ ConsoleSink    │→ Unity Console
│ （静态门面，      │──▶│   Router     │──▶│（主线程）       │   (Debug.Log*)
│  可编译期剥离）   │   │  分级/开关    │   └────────────────┘
├──────────────────┤   │  模块过滤     │   ┌────────────────┐
│ IZLogger（注入） │──▶│  分发到 Sink  │──▶│ FileSink       │→ zipper-*.log
│ （模块化、可测）  │   └──────────────┘   │（后台线程+缓冲） │   (persistentDataPath)
└──────────────────┘                      └────────────────┘
```

**双入口**（关键设计，二者不可互相替代）：

| 入口 | 用于 | 能否编译期剥离 | 特点 |
|---|---|---|---|
| `ZLog`（静态门面） | 框架与业务普通调用点、热路径 | ✅ 能（`[Conditional]` 只对静态调用生效） | 零依赖、随处可用 |
| `IZLogger`（注入） | 模块化日志、需要 mock 的单测 | ❌ 不能（接口调用运行时才解析） | 靠 `IsEnabled` 前置判定 + 运行时过滤 |

> **热路径用门面 + 前置判定；需要注入/测试的场合用 `IZLogger`**。两者最终汇入同一 Router 与 Sink 链。

### 3.3 分级策略（剥离 × 运行时开关）

| 级别 | 编译期（Release） | 编译期（Editor/Development） | 运行时默认 | 典型用途 |
|---|---|---|---|---|
| Trace | 剥离 | 保留 | 关 | 逐帧/逐次调用的细节 |
| Debug | 剥离 | 保留 | 关 | 开发期调试 |
| Info | 剥离 | 保留 | 开 | 关键流程节点 |
| Warn | **保留** | 保留 | 开 | 可恢复的异常（如句柄泄漏兜底） |
| Error | **保留** | 保留 | 开 | 失败路径 |
| Fatal | **保留** | 保留 | 开 | 不可继续（伴随抛异常/退出） |

- 剥离由编译符号控制（如 `ZIPPER_LOG_VERBOSE`）：编辑器与 Development Build 定义，正式构建不定义。
- **两套机制的关系**：编译期剥离 = 连调用都不存在（参数不求值、零成本）；运行时开关 = 编译进来了但被过滤。剥离掉的级别在 Release 里**运行时也调不出来**（性能换可观测性，已确认接受）。

### 3.4 设计要素（API 形态，思路级）

| 要素 | 形态要点 | 说明 |
|---|---|---|
| 级别 | 6 级枚举，顺序即优先级 | 过滤 = 级别与阈值比大小 |
| 模块 | 枚举：Core / Pool / Resources / Audio / UI / Game | 既作日志 tag，也作按模块级别控制 |
| 日志条目 | 轻量只读结构：级别、模块、消息、时间戳、线程 ID、上下文对象 | 上下文对象（UnityEngine.Object）用于 Console 双击跳转，可空 |
| 静态门面 | 输出方法 `Trace/Debug/Info/Warn/Error/Fatal` + `IsEnabled(level, module)` + `SetGlobalLevel/SetModuleLevel` + `For(module)` | 可剥离、随处可用；`For(module)` 返回模块日志器 |
| 模块日志器 | `IZLogger`：`Log(level, msg)`、`Info/Warn/Error`、`IsEnabled(level)` | 可注入、可 mock；不可剥离 |
| 输出端 | `IZLogSink`：`Write(entry)`、`Flush()`、`RequiresMainThread` | 可插拔：Console / 文件 / 未来内存面板 |

> 说明：以上只定"有哪些概念、各自承担什么"，具体类型定义、命名与拆分由实现者决定。

### 3.5 关键流程（思路级伪代码）

> 以下用伪代码表达**做法与顺序**，不追求可编译，也不给完整实现。

#### F1 门面：三级分流

```
可剥离级别（Trace / Debug / Info）
    → 方法挂 [Conditional("ZIPPER_LOG_VERBOSE")]
    → Release 构建里：调用点、参数求值、字符串分配 一起消失

保留级别（Warn / Error / Fatal）
    → 无剥离特性，始终编译

所有级别最终 → Router.Dispatch(级别, 模块, 消息, 上下文)

热路径使用纪律：
    if (ZLog.IsEnabled(级别, 模块))        // 先判定
        ZLog.xxx($"...插值...");           // 后拼接（关闭时不分配）
```

#### F2 Router：过滤与分发

```
Router 状态：全局阈值 + 每模块阈值 + Sink 列表
IsEnabled(级别, 模块) = 级别 ≥ 全局阈值 且 级别 ≥ 该模块阈值

Dispatch(级别, 模块, 消息, 上下文)：
    1) 过滤：不满足 IsEnabled → 直接返回
    2) 组装日志条目：级别 / 模块 / 消息 / 时间戳 / 线程 ID / 上下文
    3) 遍历 Sink：
         Sink 要求主线程 且 当前非主线程 → 投递到主线程泵
         否则                          → 直接 Write
```

#### F3 ConsoleSink：映射到 Unity Console

```
RequiresMainThread = true（Debug.Log 只允许主线程调用）

Write(条目)：
    文本 = "[时间] [Zipper.模块] 消息"（可加富文本着色）
    按级别映射：Warn → LogWarning；Error/Fatal → LogError；其余 → Log
    把上下文对象一并传入 → 支持 Console 双击跳转
```

#### F4 FileSink：后台写 + 缓冲 + 轮转

```
Write(条目)，任意线程：
    格式化一行 → 入并发队列
    队列达到上限 → 丢弃最旧（防止日志爆炸拖垮游戏）

后台线程循环：
    等待信号（或超时，如 500ms）         ← 攒批，减少 IO 次数
    批量出队 → 拼进缓冲 → 写文件
    单文件超过上限（如 2MB）→ 轮转新文件 + 清理超出保留数的旧文件

Flush()：
    把剩余缓冲全部写出（退出时调用，带超时防卡死）
```

#### F5 主线程泵：保证 Console 输出合法

```
初始化时记录主线程 ID
非主线程产生的"主线程专用输出" → 入队
驱动对象每帧（Update）清空队列 → 在主线程执行真正的 Write
注意：顺序按入队先后保持，不丢不乱
```

#### F6 运行时级别控制

```
SetGlobalLevel(级别)              // 全局阈值
SetModuleLevel(模块, 级别)        // 单模块覆盖全局

语义提醒：只能影响"编译进来的级别"——
Release 构建里 Info 及以下已被剥离，调级别也无法让它们出现（预期行为）。
```

#### F7 初始化与关闭

```
Initialize(选项)：
    1) 装主线程泵（记录主线程 ID + 创建常驻驱动对象）
    2) 建 Router 与 Sink（ConsoleSink 必装；FileSink 按配置）
    3) 门面接入 Router
    4) 注册退出回调 → 退出前 Flush（防丢尾日志）

Shutdown()：
    Flush 全部 Sink → 停止后台线程（Join 带超时）→ 移除驱动对象

未初始化时的降级：门面自带默认 Router（仅 Console、Info 级），任何时刻调用都不报错。
```

### 3.6 关键坑（实现时逐条对照）

| # | 坑 | 规避 |
|---|---|---|
| 1 | `$"..."` 插值在判定前就分配 | 热路径先 `IsEnabled` 再拼接（F1） |
| 2 | `[Conditional]` 只对**静态调用**生效 | 注入路径（`IZLogger`）不能剥离，必须靠运行时判定 |
| 3 | 后台线程调 `Debug.Log` 行为未定义 | Console 走主线程泵（F5） |
| 4 | 文件 IO 阻塞主线程 | 后台线程 + 队列 + 批量写（F4） |
| 5 | 日志爆炸拖垮游戏 | 队列上限丢最旧 + 单文件上限轮转 + 旧文件数量上限 |
| 6 | 日志系统自身抛异常 | Sink 内部吞异常并降级（绝不让日志搞崩游戏） |
| 7 | 退出丢尾日志 | 退出回调 + Scope Dispose 双保险 Flush |
| 8 | 移动平台写盘路径/权限 | 只用 `persistentDataPath`；启动自检失败则禁用文件输出 |
| 9 | Fatal 后继续运行 | 记录后由调用方决定抛异常/退出（日志不代劳） |

### 3.7 验收标准与测试点

| 验收点 | 测试场景 | 断言 |
|---|---|---|
| 分级过滤 | 设全局=Warn 后调 Info/Warn | Info 不输出、Warn 输出 |
| 模块级别 | 全局 Warn，但 Resources 设 Debug | Resources 的 Debug 输出，Pool 的不输出 |
| 编译期剥离 | Release 构建调 Trace/Debug/Info | 调用点与字符串分配在 IL 中不存在 |
| 文件输出 | 写 100 条日志后 Flush | 文件含 100 行、格式与时间戳正确 |
| 线程安全 | 后台线程写 1000 条 | 不抛异常、条数符合上限策略、Console 在主线程输出 |
| 轮转 | 写入超单文件上限 | 生成新文件、旧文件按上限清理 |
| 退出不丢 | 写日志后立即退出 | 退出后文件含尾部日志 |
| 健壮性 | 目录只读 / 磁盘满 | 不抛异常，文件输出自禁用并 Warn 一次 |

## 4. 其它模块（简述）

### 4.1 ZAssert（断言/守卫）

- 思路：条件编译断言——编辑器/开发构建下中断定位；Release 下**降级为 Error 日志**，不中断玩家。
- 与日志系统的关系：断言失败最终也走 `ZLog`，所以 Assert 依赖 Logging 先行。

### 4.2 Extensions（按需增补，禁止堆砌）

- Unity 对象空判断（正确处理 Unity 的"假 null"）——**这个必须有**，其它用到再加
- Transform / GameObject / 集合 / 字符串扩展：有真实复用场景才加

### 4.3 事件总线（双实现：自研 + R3 封装，v0.5 定案）

**为什么做**：跨模块的"低频通知"需要解耦（资源加载完成、场景切换、UI 面板开关、音频状态、池统计……）。模块之间直接用引用会形成横向依赖；总线注册进 IoC，各模块按需注入使用。

**双实现结构（v0.5 使用者决策）**：

```
IZEventBus（接口，定义在 Zipper.Core —— 零依赖，任何层都能用）
   ├─ ZEventBus（自研实现，放在 Zipper.Core）
   └─ ZR3EventBus（封装 R3 的实现，放在依赖 R3 的程序集：Zipper.UI 或独立的 Zipper.Events.R3）
```

> **命名约定**：品牌名 Zipper 取首字母 **Z** —— 框架自有类型用 `Z*` 前缀（`ZLog`、`ZEventBus`、`ZResourceManager`、`ZObjectPool`），接口用 `IZ*`（`IZLogger`、`IZEventBus`、`IZResourceManager`）。详见 `docs/standards/naming-convention.md`。

- **接口在 Core、R3 实现不在 Core**：Core 保持"零框架依赖"，若把 R3 实现塞进 Core，就等于 Core 被迫引 R3，地基原则破功。
- **选择方式**：由组装层（Zipper.Runtime / GameLifetimeScope）决定注册哪个实现；两个都要用时用容器的**带 key 注册**区分（具体 API 以实现时的容器版本为准），使用方按 key 取用。
- **R3 在本框架的定位（使用者决策）**：**只负责 UI 方面的事件通知**（UI 绑定、面板与 ViewModel 之间的通知），不承担全框架总线职责。

**用途边界（硬纪律，须写进编码规范）**：

| 场景 | 用什么 |
|---|---|
| 跨模块"某件事发生了"的低频通知 | ✅ 事件总线 |
| 要对方做事并拿结果 | ❌ 接口方法 + UniTask 返回值 |
| 查对方状态 | ❌ 属性 / 查询接口 |
| 每帧、高频数据流（输入、坐标、插值、进度） | ❌ R3 流 或 直接引用 |
| 同模块内部函数间调用 | ❌ 直接调用 |

**实现选择与归属纪律（硬规则）**：

| 场景 | 用哪个 |
|---|---|
| UI 相关通知（面板开关、ViewModel 通信、UI 生命周期） | **ZR3EventBus**（UI 模块本就依赖 R3） |
| 非 UI 的跨模块通知（资源、场景、音频、池） | **ZEventBus**（自研，零依赖） |
| 高频响应式数据流（输入、坐标、插值、进度） | **R3 流**（`ReactiveProperty`/`Subject` + 操作符），不经总线 |
| 请求-响应、状态查询、模块内调用 | 接口方法 / 查询接口 / 直接调用——**不用总线** |

- **同一事件类型只归属一条总线**；**不允许同一个事件同时发到两条总线**（订阅者会收到两次，且两条总线的顺序/异常语义不同）。
- 允许"两条总线并存、各管一类事件"；不允许"同一事件双发"。
- 两个实现**对外行为必须一致**（发布/订阅/退订/异常隔离/主线程约定），并用**同一套测试**覆盖——切换实现不应让行为漂移。

**设计要素**：

| 要素 | 形态要点 |
|---|---|
| 接口 | `IZEventBus`：发布（泛型）+ 订阅（泛型，返回**可释放的订阅凭据**） |
| 类型化 | 泛型方法 + 每事件类型一个通道；零装箱、零反射 |
| 分发 | 同步、立即；发布时对订阅者做**快照**，允许订阅者在回调内退订/新增而不破坏遍历 |
| 异常隔离 | 单个订阅者抛异常 → 记日志后**继续**通知其余订阅者 |
| 线程 | 默认主线程发布；后台线程发布经主线程泵（与日志系统同一套机制） |
| IoC | 注册为 **Scope 单例**，模块按注入获取 |
| 生命周期 | 订阅凭据建议登记到 Scope 级容器，Scope 关闭统一释放（**防泄漏兜底**） |
| 调试（可选） | 调试模式下记录最近 N 条事件与各事件订阅者数量 |

**R3 封装实现的设计要点（只做 UI 通知，但质量要与自研版一致）**：

- **对外可暴露 R3 能力**：订阅侧按需拿到 `Observable<T>`，从而使用 `Where`/`Throttle`/`Merge`/`ObserveOn` 等操作符——这是 R3 实现相对自研版的核心价值（UI 侧的节流、合并、组合）。
- **异常隔离必须自己补**：Rx 语义中流的异常（`OnError`）会终止该流，与我们要的"单个订阅者抛异常 → 记日志后继续通知其余"不同。建议形态：**内部分发仍用自研的订阅者列表 + 逐个 try/catch，对外再包装成 R3 可观察对象**——既保留操作符能力，又保住异常隔离纪律。
- **主线程约定不变**：默认主线程发布，后台线程发布经主线程泵（与日志系统共用机制）；如需 R3 调度器，由使用方在订阅链上显式指定，不在总线内部隐式切换线程。
- **不引入"当前值/粘性"语义**：需要当前值的场景直接用 R3 的 `ReactiveProperty`，不要给总线加粘性事件（避免两套语义混用）。
- **依赖边界**：`ZR3EventBus` 所在程序集引 R3；使用方若只注入 `IZEventBus` 接口，则不必引 R3（换实现时调用方零改动）。

**明确不做（v1）**：优先级、粘性/回放事件、谓词过滤订阅、异步分发、持久化、**事件继承匹配**（只按精确类型匹配，避免"基类事件被所有子类订阅"的隐式行为）。

**思路级伪代码**：

```
订阅 Subscribe<T>(handler)：
    取（或创建）T 类型对应的通道 → 把 handler 加入订阅者列表
    → 返回凭据：其 Dispose 时把该 handler 从列表移除

发布 Publish<T>(evt)：
    取 T 通道；无订阅者 → 直接返回（零分配路径）
    → 对订阅者列表做快照
    → 逐个调用；单个抛异常 → 记日志，继续下一个

线程：
    非主线程调用发布 → 投递到主线程泵 → 在主线程执行上述分发
```

**风险与纪律**：
- **隐式控制流**：谁触发、谁响应不易读 → 事件类型集中登记（统一命名空间/目录），命名用过去式（如 `ResourceLoaded`）。
- **订阅泄漏**（最大坑）：凭据必须释放；Scope 级统一回收兜底。
- **事件爆炸**：一条流程串起多个事件 = 调试地狱 → 只用于"通知"，流程编排交给显式调用。

**验收点**：订阅/发布/退订正确（退订后不再收到）；发布中订阅或退订不抛异常（快照语义）；单个订阅者抛异常时其余仍收到；Scope 关闭后无残留订阅；高频发布不产生每帧堆分配。

### 4.4 工具

- 框架版本常量（随包分发便于排查问题）
- 时间 / 随机 / 路径小工具：**按需**

## 5. 工程接入要素

### 5.1 目录与文件布局（建议）

```
Assets/Zipper/Core/
├── Zipper.Core.asmdef
├── Logging/
│   ├── 门面（ZLog）
│   ├── 模块日志器（IZLogger 及其实现）
│   ├── Router（分级 / 模块过滤 / 分发）
│   ├── Sink 抽象 + Sinks/（Console、File）
│   ├── 数据（级别、模块、日志条目）
│   ├── 选项与引导（初始化 / 关闭）
│   └── Internal/（主线程泵 + 常驻驱动对象）
├── Assert/
├── Extensions/（按需）
└── Utils/
```

- 命名空间：`Zipper.Core`，Logging 子目录用 `Zipper.Core.Logging`；**目录与命名空间保持一致**。
- 文件如何拆（一类型一文件或多类型合并）由实现者定。

### 5.2 asmdef 配置要点

| 项 | 取值 | 说明 |
|---|---|---|
| name | `Zipper.Core` | 已存在 |
| references | **空** | 只依赖引擎；不引 UniTask / VContainer / Addressables（§1 依赖原则） |
| autoReferenced | true（默认） | 让 Assembly-CSharp（业务/DI 层）可直接使用 |
| includePlatforms | 全平台 | 编辑器专用代码（如日志 Viewer）将来放 `Zipper.Editor` |
| allowUnsafeCode | false | 无需 |

> 若将来确实要引 UniTask（如异步 flush），再补 references，同时更新 §1 的 roadmap 偏差记录。

### 5.3 初始化与关闭时序

```
游戏启动
 └─ 引导入口（当前 GameLifetimeScope.Awake；将来 Zipper.Runtime 引导组件）
      ├─ 1) 初始化日志系统（越早越好，先于任何业务日志）
      │       装主线程泵 → 建 Router/Sink（Console 必装、文件按配置）→ 门面接入
      ├─ 2) 注册退出 Flush（防丢尾日志）
      └─ 3) 容器注册（可选）：把模块日志器 IZLogger 注册进容器供各模块注入

Scope 关闭 / 应用退出
 └─ Flush 全部 Sink → 停后台线程（Join 带超时）→ 移除驱动对象
```

要点：
- **初始化必须早于任何业务日志**（放在 `Configure` 之前更稳妥）。
- **驱动对象**：不引 UniTask / VContainer 的前提下，用一个常驻不销毁的极简驱动对象每帧清空主线程队列；编辑器下需考虑 domain reload 后重建。
- **退出不卡死**：后台线程 Join 设超时，超时即放弃剩余缓冲。

### 5.4 与 GameLifetimeScope 的接入关系

```
GameLifetimeScope（Assembly-CSharp，现状）
 ├─ Awake      ：初始化日志系统（v1 阶段手工调用）
 ├─ Configure  ：注册 IZResourceManager→ZResourceManager（单例）
 │               注册 ResourcesBootstrapper（入口点）
 │               （可选）注册 IZLogger 供注入
 └─ 将来       ：改由 Zipper.Runtime 的引导组件统一装配（业务工程零改动）
```

- **模块取 tag**：各模块通过模块日志器或门面指定自己的模块枚举；**框架内部普通调用建议用门面**（可剥离），**需要 mock 的单测用注入的 `IZLogger`**。
- **第一个真实用例**：在资源管理器的初始化前后打点，记录 Addressables 初始化耗时。

### 5.5 裁剪与共存

- Core 无框架依赖 → 任何层次都可引用；某模块不用日志时无需改动（无强制引用）。
- 与 Unity 自带 `Debug.Log` 共存：框架代码统一走日志门面，第三方/Demo 代码可直接用 `Debug.Log`。
- 现有调用点衔接：`ZResourceManager` 的 `Debug.LogWarning` 与两处 TODO，**由使用者实现日志系统时**自行替换。
