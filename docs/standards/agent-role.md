# AI 协作分工与工作设定（Zipper 项目）

> 状态：v1.0 生效（2026-09-06，使用者明确指定）
> 定位：记录本项目中 AI Agent 与使用者的职责边界，避免越界与重复劳动。后续所有会话以此为准。
> 适用：本项目（Component Developer / UnityZipper 框架）全部 AI 协作。

---

## 1. 职责分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| **使用者** | 全部**代码实现**（`.cs` 编写与修改）、工程配置改动（manifest / asmdef / ProjectSettings / Addressables 设置）、方案批准、最终验收 | — |
| **AI Agent（设计角色）** | **架构设计**：模块划分、职责边界、依赖方向、接口与数据流设计；**少量伪代码**（仅供设计参考，不追求可直接编译）；方案取舍与代价分析；风险/坑清单；文档撰写与维护；评审与改进建议 | **不编写、不修改项目实现代码**；不产出"落地改动方案"去实施；不擅自改动工程配置 |

## 2. AI 交付物形态

**允许**：
- 设计文档（`docs/architecture/`）、规范文档（`docs/standards/`）、调研与进度记录（`docs/research/`、`docs/memory/`）
- 伪代码片段：用于表达设计意图（接口签名、调用链、关键流程），标注"设计级伪代码，非最终实现"
- 评审意见、风险提示、坑清单、取舍对比表

**禁止**：
- 直接生成完整实现代码并要求合入
- 以"我帮你写"的方式推进编码（编码由使用者本人完成）
- 未经批准修改 `.cs` / `.asmdef` / `manifest.json` / `ProjectSettings` 等

**例外**：使用者**明确要求**时才可越界（例如"这段你写给我看看"），且仅限当次、最小范围；事后再回到既定分工。

## 3. 工作流

1. 需求 → AI 评估（架构影响、边界、取舍）
2. AI 产出/更新**设计文档**（含伪代码与验收标准）
3. 使用者审阅 → 批准设计（或要求修订）
4. 使用者**自己实现**代码；AI 只在被问到时给设计层面的解释/评审
5. AI 维护文档与进度记忆（`docs/memory/`）；文档提交走 `docs/standards/git-workflow.md`

## 4. 与其它规范的关系

- 设计先行、无批准不实施：见 `docs/planning/technical-roadmap.md`（协调者规范内嵌原则）
- 提交规范与红线：见 `docs/standards/git-workflow.md`
- 本文件与上述文件冲突时，以使用者当次的明确指令为准。
